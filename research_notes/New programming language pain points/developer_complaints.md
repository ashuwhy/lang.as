## 1. Headline industry surveys and rankings (Stack Overflow, JetBrains, Octoverse, TIOBE/RedMonk/IEEE)

### Takeaway
Across the big surveys, technical debt and build/deploy complexity lead the chronic complaints (SO 2024: 62% technical debt, about 33% each for build and deploy stack complexity). Since 2023 a new complaint has grown fast: AI output that is "almost right." Trust in AI is falling even as use rises (84% use, 46% distrust, favorability down from 77% to 60%). On language popularity, the shift runs toward Python (AI/data) and TypeScript (typed, AI-friendly). TypeScript became GitHub's #1 language in August 2025.

### Inferences
- The most widely felt frustrations are not tied to any one language. They are technical debt (62%) and build/deploy stack complexity (about 33% each). A language can address these only indirectly, through refactorability, strong types and an integrated toolchain.
- Admiration and adoption are split. Rust leads "admired" year after year, but Python and TypeScript win on usage. A new language that people admire, but that costs a lot to adopt, is likely to repeat Rust's pattern.
- GitHub's own explanation for TypeScript's rise (typed languages make agent-written code more reliable) is the clearest link between the AI era and language design in the data.

## 2. Per-language pain points

### Takeaway
Each ecosystem has a chronic complaint that survives year after year. Python: packaging/environments, performance and the GIL, typing gaps. JavaScript: lack of static typing and build-config complexity. C/C++: memory safety, dependency management, build times. Rust: compile times and complexity. Go: error-handling verbosity and missing sum types. Swift: the strict-concurrency migration. Several were big enough to prompt major rewrites or decisions in 2025: TypeScript's compiler moved to Go (10x faster); Python's free-threaded build was officially supported in 3.14; Go ruled out error-syntax changes; C++ dropped Safe C++.

In open-text answers, the missing features are mostly **error handling/reporting, enums and sum types, nil-pointer safety**, and general verbosity. — [go.dev 2025 survey results](https://go.dev/blog/survey2025); [ASCII News](https://ascii.co.uk/news/article/news-20260123-02a0ff86/go-developer-survey-reveals-idioms-error-handling-pain-point); [Lobsters](https://lobste.rs/s/oq8n8r/results_from_2025_go_developer_survey)

- [EVENT] On 2025-06-03 the Go team (Robert Griesemer) announced that "for the foreseeable future" it will stop pursuing syntax changes for error handling and close all such proposals without further investigation. Earlier proposals had failed: check/handle, the `try` builtin and the `?` operator. Error handling was acknowledged as the top complaint in user surveys. Every Go user the team spoke with at Google Cloud Next 2025 opposed changing the language for it. — [go.dev "[ On | No ] syntactic support for error handling"](https://go.dev/blog/error-syntax)

#### Swift, Java/Kotlin, C#
- [ANECDOTE] Swift 6 strict concurrency: developers report thousands of new diagnostics. One report cites 20,000 warnings on one legacy module; another cites 76 errors and 238 warnings. There is "whack-a-mole" `@MainActor` annotation, and one migration touched 79 files and about 2,800 lines. Swift 6.2 (Sept 2025) added "approachable concurrency" to ease this. Posts such as "Swift Concurrency is a Mess in 2026" say trust in the model has eroded. — [dev.to "Swift 6 turned working code into a compile error"](https://dev.to/adioof/swift-6-turned-working-code-into-a-compile-error-and-ios-devs-are-furious-39o9); [Swift Forums](https://forums.swift.org/t/is-there-a-way-to-use-swift-6-without-swift-strict-concurrency-complete/74677); [NativeFirst on Swift 6.2](https://nativefirstapp.com/blog/swift-6-2-approachable-concurrency-migration-guide/); [Apple docs](https://developer.apple.com/documentation/swift/adoptingswift6)
- Java/Kotlin and C#: no sourced data retrieved (see Gaps).

### Inferences
- The strongest *language-level* complaints are those where a language fix exists and people are asking for it:
  - Go wants sum types, better errors and nil safety.
  - JavaScript wants static types, which TypeScript already answers.
  - C/C++ wants memory safety, which the Android data shows works when you change language.
  - Python wants performance without the GIL, which needed language/runtime work (PEP 703).
- Rust shows that a safety fix brings new costs: compile times (about 28% "big problem"), complexity (41.6% worry) and iteration friction. A successor language would need safety *and* fast iteration.
- Toolchain speed has become a cross-language pain. TypeScript rewrote its compiler in Go, Python's most loved new tool is a Rust rewrite (uv), and Rust has a dedicated compiler-performance survey. Developers reward 10x-faster tools strongly (uv at 74% admired).
- Governance limits fixes inside existing languages. Go closed error-syntax proposals, and C++ rejected Safe C++. Some chronic complaints will not be fixed in place, which leaves room for a new language.

## 3. Cross-cutting frustrations (dependency/build hell, slow CI and compiles, onboarding, technical debt, concurrency, "works on my machine," polyglot context switching, config languages)

### Takeaway
The cross-cutting data point to friction around *code*, not in writing it: technical debt, build/deploy complexity, finding information, context switching, and slow feedback loops. Dependency/build hell appears in every ecosystem's own survey (Python uv, C++ package management, JavaScript build config, Rust disk use and rebuilds). The "two-language problem" (Python on top, C++/CUDA underneath) is a structural, language-level pain that Mojo is explicitly built to fix.

### Cited Findings
- [SURVEY] Atlassian State of DevEx 2025: 50% of developers lose 10+ hours per week to inefficiencies, and 90% lose 6+ hours. ### Inferences
- "Build/dependency/toolchain friction" is the most-cited cross-ecosystem pain that a *language project* can realistically own. Evidence:
  - Ecosystems with a single official toolchain (Cargo, Go modules) complain about compile speed, not about fragmentation.
  - Ecosystems without one (C++, Python before uv, JavaScript) complain about fragmentation and configuration.
  - A new language that ships one fast build, package and test tool from day one sidesteps this pain. However, uv shows a *tool* can also fix it inside an existing language, which weakens the case for a new language.
- Onboarding and "finding information" (Atlassian's #1) and technical debt (SO's #1) are mostly organizational. A language helps only at the edges: explicit types, refactor-safe semantics, and less implicit magic.
- The Python + C++/CUDA split affects the fastest-growing population (AI/ML; Python +7 pts in SO 2025, Jupyter +92% on GitHub 2024). No library or tool can remove it, because the split is about one language's semantics being unable to express high performance. It is a true language-level problem, and a well-funded contender (Mojo) is already attacking it.

### Gaps
- No survey numbers found for: time lost to slow CI specifically, onboarding time into large codebases, frequency of "works on my machine" incidents, and debugging-concurrency pain across languages.
- No quantitative survey on YAML/config pain was found. Evidence is anecdotal (HN threads, blog posts).
- No quantitative data on how many developers regularly switch between Python and C++/CUDA. The Mojo framing is a vendor claim.
- DORA 2025 (AI-assisted software delivery) was not retrieved.

## 4. Chronic pain points vs. new ones since AI tools spread

### Takeaway
The chronic set is stable across 2023–2026. It includes technical debt; build and dependency complexity; slow compiles (Rust #1 complaint "third year running"); Go's error handling (acknowledged top complaint for years); JavaScript's lack of static typing (still #1); C/C++ memory safety (about 70% of CVEs "for 12 years"); and Python packaging and performance. New since 2023 is a cluster around AI: output that is almost right, falling trust, debugging AI code, measured slowdowns, and a move toward typed languages that constrain AI-generated code.

### Inferences
- AI moves the bottleneck from *writing* code to *verifying and reviewing* it. The chronic language pains (weak types, implicit nulls, unchecked errors, memory unsafety, undefined behavior) now hurt twice: once for humans, and again as the reason AI output is "almost right." A language whose type system and semantics let machines check AI-generated code (sum types, no nulls, explicit effects and errors, memory and data-race safety, fast compile-check loops) aims at both a chronic pain and the newest one.
- Three items look chronic *and* stuck because the governing body declined or stalled a fix: Go error handling (closed 2025), C++ memory safety (Safe C++ dropped 2025), and JavaScript static types (TypeScript sits outside the language, and TC39 type annotations are unshipped). These are the openings where a new language does not compete with an in-place fix.

### Gaps
- There is no single longitudinal dataset tracking the same "frustration" question across SO 2023–2026. SO 2025 and 2026 work-frustration numbers were not retrievable.
- No survey quantified how much AI-generated-code debugging varies *by language* (e.g., whether typed languages reduce "almost right" errors). The Octoverse claim is correlational, and GitHub gives it as an explanation.

## 5. Ranking: breadth of impact × whether a *language* (vs. library/tool) is the right fix

### Takeaway
Weighing how many developers are affected against whether a new language is the correct fix points to two candidates. The first is **verifiable correctness for AI-era code**: strong static guarantees plus fast check loops, so "almost right" code fails at compile time. The second is **a memory- and data-race-safe systems language that keeps Rust's guarantees without its compile-time and complexity costs**. The two-language (Python ↔ C++/CUDA) problem is a strong third, narrower but clearly language-level. Packaging and build hell affects many people but is increasingly being fixed by *tools* (uv, Vite, TypeScript-Go), so it is a weak reason to create a language.

### Cited Findings
Evidence is summarized from §§1–4. Ranked by estimated breadth, with a language-fixability judgment.

|---|---|---|---|

| 2 | AI output "almost right" / low trust / debugging AI code | 84% use AI, 46% distrust, #1 AI frustration ([SO 2025](https://stackoverflow.co/company/press/archive/stack-overflow-2025-developer-survey/)); 19% slowdown ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)) | **Plausibly yes.** Typed languages are already credited for AI reliability ([Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)). |

### Inferences
- Where a new language has the clearest opening, the complaint is broad, a language is the proper fix, and existing languages have declined or stalled the fix. Rows 2, 4+5+6 combined, and 7 meet all three conditions.
- Rows 4–6 together describe "Rust's promise without Rust's tax." Rust is the most admired language (72%), but its own users worry about complexity (41.6%) and compile times (27.9%). That makes it a well-evidenced gap.
- Row 2 is the newest and grows with AI adoption (84%). But the proof that *language* design reduces AI errors is inferential. It rests on GitHub's reasoning about TypeScript, not on controlled data.

### Gaps
- No survey directly measures what share of *all* developers are hurt by memory safety, compile times or the two-language problem. The breadth estimates are inferred from population sizes (C/C++ users, Rust users, Python/AI users) and per-community surveys.
- Unverified: whether typed or safer languages measurably reduce AI-code defects. This is a key assumption for row 2 and needs a primary study.
