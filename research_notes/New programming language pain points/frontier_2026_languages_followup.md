### Inferences
- The 94% figure is narrower than GitHub's framing suggests. It is the share of *compilation errors* (not of all bugs) in TypeScript generated by open-weight models of 2B–34B parameters on the paper's benchmarks. It says type errors dominate what a compiler catches in LLM output. It does not say typed languages reduce overall defects, which remains the unverified assumption flagged in `developer_complaints.md`.
- The same paper shows a language-side fix works: constraining decoding with the type system halves compile errors. For a new language, a type system simple enough to drive constrained decoding is a concrete, evidence-backed design goal.

### Inferences
- **The funded and the fast are shipping; the careful are slipping.**
  - AI-era entrants shipped usable versions within weeks of their first commit: Zero (May 2026 to v0.3.4 by September), Rue (a compiler in 11 days), Nanolang, and Bend 2.
  - Long-running projects keep moving their first stable milestone: MoonBit 1.0 (H1 to Q3 2026, still unshipped), Roc 0.1 (7 years in, now "later in 2026"), Carbon 0.1 ("end of 2026 at the soonest"), and Verse's open-source release (dropped from the roadmap).
  - AI agents compress compiler construction. They do not compress stabilisation, ecosystem building or corporate governance.
- **"Language for AI" is now the default pitch for 2026 launches.**
  - Zero: JSON diagnostics and graph patches.
  - Bend 2: LAWS.bend proofs.
  - Nanolang: mandatory tests.
  - CodeSpeak: specs compiled by an LLM.
  - MoonBit: an "AI-native" toolchain.
  - A new entrant needs a differentiator beyond this label.
- **Distribution choices differ sharply.**
  - Zero and Bend 2 use curl installers and GitHub releases. Neither is on npm or crates.io.
  - CodeSpeak ships as a PyPI thin client to a hosted service. That is closer to a SaaS than a language, and its PyPI cadence stopped after 2026-05-21.
  - Mojo (earlier round) reached 1.0 on PyPI.
  - For the report's recommendation, publishing through an existing package manager remains the cheap, proven channel.
- **Name collisions are a real risk:** a "Rue" already exists on crates.io with 32k downloads. A new language should check registry names before launch.

## 7. LLMs and new or low-resource languages

### Takeaway
- **JAXBench (arXiv 2607.20466)** gives the clearest number.
  - Pallas, the TPU kernel DSL, is rare in training data, so models "routinely hallucinate Pallas APIs".
  - Conditioning on curated TPU documentation raised per-sample correctness **from 5.8% to 37.3%**, solving 48 of 50 workloads.
- **"No Resource, No Benchmarks, No Problem?" (arXiv 2606.16827)**:
  - It translates HumanEval, MBPP and McEval-Hard into Gleam and MoonBit.
  - It finds that further pre-training gives the largest gains but damages instruction-following in instruction-tuned models. The fix is to pre-train a base model and then transfer instruction-following by weight diff.
  - Its numeric results were not visible in two searches.
- **MultiPL-T** is OOPSLA 2024. It covers Julia, Lua, OCaml, R and Racket, and reports state-of-the-art fine-tunes. Its gain numbers were not visible.

### Inferences
- **The documentation lever is measurable and cheap.** In JAXBench, putting curated docs in context gave about a **6.4× rise in per-sample correctness** (5.8% to 37.3%; my arithmetic) for a DSL that models rarely see. For a new language, shipping compact, LLM-ingestible reference docs and agent skills, as MoonBit already does, is the lowest-cost fix for the "no training data" problem. It is supported by a 2026 measurement, not only by assertion.
- **Retraining is possible but has side effects.** The no-resource paper shows further pre-training helps most, but it breaks instruction-following unless it is done on a base model and then merged. This is within reach of a language team with modest GPU budget only if an open base model is used. MultiPL-T's earlier cost estimate (in `new_languages_adoption.md`, about 550 A100-days to reproduce) still stands as the only cost figure.
- **Type checkers catch LLM errors, and they generalise across languages.** JAXBench's failure modes include annotations "that do not type-check", and Mündler et al. (section 1) found 94% of TypeScript compile errors were type errors. Both support a language whose type system gives the model precise, machine-readable feedback.

### Gaps
- All numeric pass@k results for Gleam and MoonBit (arXiv 2606.16827) and for MultiPL-T. The report should state the direction of the effects (a large gap for no-resource languages; pre-training helps most) and quote only the JAXBench numbers, labelled as single-search snippet evidence.
