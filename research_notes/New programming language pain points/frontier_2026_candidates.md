## A. Verification-first language for AI-written code (contracts and effect signatures as the review surface, SMT verdicts, agent code rejected unless it meets its contract)

### Takeaway
This is now the most crowded and best-funded of the five spaces. Formal verification for AI-written code attracted hundreds of millions of dollars in 2026: Axiom raised $200M at a valuation above $1.6B, Tessl has raised about $125M, Qodo $70M, plus several seed rounds. Several new languages ship the exact pitch: Bend 2 ("blocks AI mistakes via proof", September 2026), Vera (contracts + effects + Z3 + Wasm), Vercel Zero (explicit effects, JSON repair plans) and MoonBit (AI-native toolchain with formal verification added in 0.9). The incumbents' results are strong: AWS runs a Dafny-verified authorization engine at 1 billion calls per second, and LLMs now reach 82% (Dafny), over 80% (Verus systems proofs) and 85–87% of specs (Lean, repository scale) on verification benchmarks. What is still unshipped is a verified language that (1) writes to a mainstream host (TypeScript/npm, Python), (2) makes a short contract and effect signature the thing a human reviews, (3) forbids an agent from weakening that contract, and (4) has real users. No project combines all four with traction. Vera, the closest match, is a single-author project whose benchmark is self-reported.

**The author's own evidence (from HANDOFF.md, summarising the SepInfer paper)**
- When an LLM is asked to make a sound verifier pass, it "weakens the spec until the bug disappears", so SepInfer needed a "floor guard" that forbids relaxing declared contracts. NOTES (`HANDOFF.md`)

### Inferences
- The "language for AI-written code" category now exists and is being fought over by funded teams: HOC/Bend 2, Vercel/Zero, MoonBit, Axiom (Lean, not a new language) and AWS/Kiro plus Dafny. A new entrant has to differentiate on something they lack, not on the category. Two gaps are visible. (1) None of the new languages targets TypeScript/npm or Python as the output. Bend 2 runs on its own runtime, Vera and MoonBit target Wasm, Zero and Nanolang target native code or C. (2) None advertises protection against *spec weakening*, which the author's SepInfer work found to be the default LLM behaviour. A checker that pins contracts, so an agent cannot rewrite the spec it is judged against, is not advertised by any competitor I found.
- Benchmark results suggest the language matters as much as the model: the same task class scores 82% in Dafny and 27% in Lean. A new verification language will start below Dafny, because models have no training data for it, unless it looks like Dafny, TypeScript or Python.
- On verifier speed, the evidence points to per-function verdicts in about 1–10 seconds, not minutes. AutoVerus's median task finishes in under 30 s *including* LLM calls, so SMT time has to be a small share of that. Repository-scale work (Vero) fails because proofs and code fall out of sync, not because the checker is slow. That argues for modular, per-function contracts that are cheap to re-check.
- Solo or small-team odds: building a prototype is clearly possible (Vera is a one-person side project with 9 PyPI releases in 5 weeks). Winning adoption is less likely: the space draws $100M-scale funding, big-company sponsors (AWS, Microsoft, Vercel) and a founder with a huge audience (HOC). A small team's realistic route is a narrow wedge that these players do not cover (see E and the compile-target section).

## B. Capability-safe language (no ambient authority) against software supply-chain attacks

### Takeaway
The attacks keep growing. 2026 saw the Axios npm compromise, the TeamPCP compromises of Trivy, KICS and LiteLLM, and a vendor count of 2.6 times as many campaigns in the first half of 2026 as in all of 2025. But every mainstream runtime still grants permissions process-wide, not per dependency. Node's permission model became stable in v23.5/v22.13, but it is process-wide and "does not provide security guarantees in the presence of malicious code". Deno's permissions apply to the whole project. The only shipping per-package isolation in a mainstream ecosystem is LavaMoat/SES (JavaScript compartments, used by MetaMask). The component model reached WASI 0.3 in 2026, with 1.0 targeted for late 2026 or early 2027. At the language level, Austral is dormant, and the newest language with capability-passing I/O is Vercel Zero (experimental). A capability-safe language is technically well-trodden but has little competition. The hard problem is that it only protects code written in the new language, not the npm/PyPI dependencies where the attacks happen.

### Cited Findings
- **Node.js permission model**: "Stability: 2 - Stable", since v23.5.0 and v22.13.0. It is enabled with `--permission`. It is a "'seat belt' approach, which prevents trusted code from unintentionally changing files... It does not provide security guarantees in the presence of malicious code. Malicious code can bypass the permission model." It "does not inherit to a worker thread". Symlinks are followed outside granted paths, and existing file descriptors bypass it. CONFIRMED — [Node.js permissions docs](https://nodejs.org/api/permissions.html)
- **Deno**: "Permissions can only be enabled globally for the project, rather than for just one specific package". Code can "use eval, new Function, or even dynamic import or web workers to execute arbitrary code with the same privilege level". The workaround is a Web Worker with fewer permissions. Deno 2.5 added permission sets in `deno.json`. SNIPPET-CONFIRMED — [Deno security docs](https://docs.deno.com/runtime/fundamentals/security/); [Deno 2.5 blog](https://deno.com/blog/v2.5); [HN (2021, background): "Deno only has app-level permissions. We need module level too."](https://news.ycombinator.com/item?id=26091050)
- **Hardened JavaScript / SES / LavaMoat**: SES provides Lockdown, Compartments and Harden, and is the basis of TC39's "frozen realm" work. LavaMoat puts each package in its own SES Compartment and runs at install, build and run time. It is "protecting tens of millions of users at MetaMask". SNIPPET-CONFIRMED — [Stack Harbor](https://stackharbor.com/en/knowledge-base/nodejs-supply-chain-security-lavamoat/); [MetaMask news](https://metamask.io/news/using-lavamoat-to-solve-software-supply-chain-security); [Hardened JavaScript](https://hardenedjs.org/); [lavamoat on npm](https://www.npmjs.com/package/lavamoat)

SNIPPET-CONFIRMED — [WASI.dev 0.3](https://wasi.dev/releases/wasi-p3); [Bytecode Alliance](https://bytecodealliance.org/articles/WASI-0.3); [WASI roadmap](https://wasi.dev/roadmap)

SNIPPET-CONFIRMED — [ICSE 2021](https://2021.icse-conferences.org/details/icse-2021-papers/37/Containing-Malicious-Package-Updates-in-npm-with-a-Lightweight-Permission-System); [NSF PAR](https://par.nsf.gov/biblio/10302333-containing-malicious-package-updates-npm-lightweight-permission-system)
- **Package managers are responding with install-time controls, not capabilities**: "pnpm v11 has the most comprehensive consumer-side security posture with script blocking and release cooldown enabled by default... the npm CLI remains the least protected." UNVERIFIED — [Mondoo](https://mondoo.com/blog/npm-supply-chain-security-package-manager-defenses-2026)
- **2026 attack volume**: in March 2026, five major attacks, including the Axios npm compromise (attributed to a North Korean actor), and the TeamPCP compromises of Trivy, KICS, LiteLLM and Telnyx. UNVERIFIED (one vendor) — [Zscaler ThreatLabz](https://www.zscaler.com/blogs/security-research/supply-chain-attacks-surge-march-2026). "The first half of 2026 alone produced 37 campaigns and 497 indexed malicious packages — 2.6 times the campaign count and 4.5 times the package volume of the entire preceding year." UNVERIFIED (vendor). It measures something different from Sonatype's 454,600 malicious packages in 2025 (NOTES, `industry_scale_pain.md`) — [Phoenix Security](https://phoenix.security/accelerating-supply-chain-attacks-npm-pypi-vsx-ai-enabled-2026/)
- **Language-level prior art**: Austral (linear capabilities; third-party dependencies "can be constrained in what types of resources they can access") has had no push since 2025-07-28 and has 1,579★. NOTES (`industry_scale_pain.md`, `new_languages_adoption.md`). Vercel Zero passes I/O through capabilities and declares effects in signatures (see A).
- **Java SecurityManager**: I could not verify its removal this session (openjdk.org was blocked and oracle.com returned 403). Earlier notes state that "Java's SecurityManager-style approaches were abandoned". NOTES; not re-checked.

### Inferences
- Demand is real and growing, and no mainstream runtime offers per-dependency least privilege. Node's and Deno's models are process-wide, and Node says outright that it does not stop malicious code. So there is room for a language that enforces capabilities between modules.
- But a new language only controls code written in it. Nearly all the attacks cited (Axios, LiteLLM, Shai-Hulud) sit in existing npm and PyPI packages. A new capability-safe language that calls npm or PyPI through FFI inherits their ambient authority unless it wraps each foreign package in a compartment (LavaMoat-style) or a Wasm component. The practical product may be a policy layer over existing packages, not a language. That is where LavaMoat, WASI and pnpm are already heading.
- Capabilities combine naturally with candidate A. An effect or capability signature ("this function may touch the network") is a review surface for AI-written code. Zero and Vera already present explicit effects as agent-facing features.
- Solo or small-team odds: the language-design part is well understood (E, Joe-E, Austral) and uncontested. The ecosystem part (a standard library and wrappers for foreign packages) is large, and past language-level efforts stalled (Austral dormant; Java's SecurityManager was reportedly abandoned).

### Gaps
- JEP 486 (removing Java's SecurityManager) and its stated reasons could not be read.
- I found no 2025–2026 product that enforces per-dependency capabilities at the language or registry level beyond LavaMoat. No data on LavaMoat adoption outside MetaMask.
- I found no study measuring what share of 2026 supply-chain payloads per-package capabilities would have stopped, as opposed to install-script blocking.
- I found no production-user data for the WASI component model.

## D. "Rust's guarantees without Rust's cost" (brief)

### Takeaway
Big sponsors are absorbing the idea into existing languages instead of leaving room for a new one. Apple's Swift shipped `Span`, `InlineArray` and opt-in strict memory safety in 6.2 (September 2025). Swift 6.4 (September 2026) added bridging from C++ `std::span`, borrow/mutate accessors and safe `RawSpan` loading. Jane Street ships OxCaml modes. The independent efforts have stalled or restarted: Vale was archived and relaunched as Valen in August 2026, Hylo is mid-rewrite, and Austral is dormant. Inko and Rue are small.

### Cited Findings
- **Swift 6.2** (2025-09-15): `InlineArray`; `Span`, "safe, direct access to contiguous memory"; "opt-in strict memory safety" that "flags uses of unsafe constructs"; Embedded Swift gains `String`, `InlineArray` and `Span`. The post does not mention `~Escapable` or lifetime dependencies. CONFIRMED — [Swift 6.2 released](https://www.swift.org/blog/swift-6.2-released/)
- **Swift 6.4** (2026-09-15): "bridges C++20's `std::span` with Swift's `Span`"; "work with values in memory without copying them" through borrow and mutate accessors; "a new safe loading API" for `RawSpan`; better Swift/Java interop. Lifetime dependencies and `~Escapable` are not mentioned. CONFIRMED — [Swift 6.4 released](https://www.swift.org/blog/swift-6.4-released/); [Swift blog index](https://www.swift.org/blog/)
- Apple rewrote its TrueType hinting interpreter "from C to memory-safe Swift" (2026-06-12). CONFIRMED (title and summary on the blog index) — [Swift blog](https://www.swift.org/blog/)
- **OxCaml** (Jane Street, open-sourced mid-2025): modes for locality, uniqueness, affinity, contention and portability (data-race freedom). NOTES (`frontier_pl_research.md`) — [Tarides](https://tarides.com/blog/2025-07-09-introducing-jane-street-s-oxcaml-branch/)
- **Hylo**: experimental, with a new compiler under way (hylo-new has 43★) and 1,557★ overall. **Vale**: archived and relaunched as **Valen** on 2026-08-15 (337★). **Inko**: 1,304★. **Rue** (Steve Klabnik, built with an AI coding agent): 1,198★. ### Inferences
- The strongest competitor is not another new language but Swift, which ships these features with Apple's backing and interop with C++ and Java. Rust itself also keeps absorbing verification tools (Verus, Flux, Kani).
- The solo track record here is poor: Vale, Austral and Hylo all stalled or reset. Rue shows an agent can build the compiler quickly, and also that the resulting safety claims need independent checking.

## E. The TypeScript angle: unsound escape hatches, their cost, and sound or verified successors

### Takeaway
TypeScript is the largest host ecosystem for a new language: it has been GitHub's #1 language since August 2025, with 2.64M monthly contributors, and TypeScript 7's native Go compiler reached GA on 2026-07-08. Its unsoundness is well known, but the measured bug cost is moderate. A January 2026 study of 633 bug reports finds type-related errors at 12.4% in TypeScript (versus about 33% in JavaScript), with tooling, configuration, API misuse and async faults dominating. The clearest 2026 security case is n8n's CVE-2026-25049: a sanitizer trusted a TypeScript `string` annotation that nothing enforced at run time, and attackers achieved RCE. The market handles type erasure with runtime validators at huge scale. Zod has about 212M weekly downloads (September 2026), and Effect passed 10M per week in April 2026. Sound alternatives that compile to JavaScript exist (ReScript 12, Flow, Dafny's JS backend, Gleam's JS target), but none has displaced TypeScript. Hegel shut down, and the TC39 type-annotations proposal has been stuck at Stage 1 since 2022. I found no study measuring how often AI-generated TypeScript uses `any` or `as`, and could not find "TypePatrol". The author's own SepInfer results are the strongest evidence that fixing soundness after the fact hits a limit.

### Cited Findings

**How often unsoundness causes bugs**
- "From Logic to Toolchains: An Empirical Study of Bugs in the TypeScript Ecosystem" (arXiv, January 2026): 633 bug reports from 16 popular repositories. Type-related errors "fell from approximately 33% in JavaScript to 12.4% in the TypeScript sample". The landscape is "dominated not by logic or syntax errors but by tooling and configuration faults, API misuses, and asynchronous error-handling issues." UNVERIFIED (one search summary, several copies of the paper; it matches the figure in the task brief) — [arXiv 2601.21186](https://arxiv.org/abs/2601.21186)
- An earlier journal study, "An empirical study on bugs in TypeScript programming language" (JSS, 2025), exists. Title only — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S016412122500113X)
- Background (2022): across 305 TypeScript projects, 79,735 `any`-rule violations were counted, "the average TypeScript app uses the any type once for every 100 lines of code." UNVERIFIED (single snippet) — [arXiv 2203.11115](https://arxiv.org/pdf/2203.11115)
- **CVE-2026-25049 (n8n)**: in versions before 2.5.2 and 1.123.17, "the sanitization function assumes keys in property accesses are strings in attacker-controlled code. This assumption is correctly encoded in a TypeScript annotation, but it is not enforced through runtime type checking." Type confusion bypassed the sanitizer, giving authenticated users RCE through a sandbox escape. The fix added a runtime type check. SNIPPET-CONFIRMED — [Het Mehta](https://hetmehta.com/posts/n8n-type-confusion-rce); [Endor Labs](https://www.endorlabs.com/learn/cve-2026-25049-n8n-rce); [The Hacker News](https://thehackernews.com/2026/02/critical-n8n-flaw-cve-2026-25049.html)

**Runtime validators that exist because types are erased**
- **Zod**: about 212M weekly downloads in September 2026 (npm trends 211,601,986; Socket 219,173,224; Snyk 213,873,599). ### Inferences
- The case for "TypeScript is unsound, so build a sound successor" is weaker than it looks on bug counts (12.4% type errors, mostly not caused by casts) and stronger on security (n8n shows an annotation trusted as a security boundary). The market's answer so far is validators at the boundary (Zod at about 200M/week), not a new language. Every sound successor (Flow, Hegel, ReScript, Elm) has stayed niche or closed.
- SepInfer's finding, that most assertions cannot be refuted soundly after the fact, implies that soundness has to be built in when code is written, not added afterwards. The plausible wedge is a verified or sound language whose output is ordinary TypeScript plus `.d.ts` files, with contracts checked statically and turned into runtime guards (Zod-like) at the untyped boundary. It would ship as npm packages that any TypeScript project can import. Nothing like that with traction turned up in this session. Dafny emits JS but I saw no npm adoption evidence, ReScript is sound but not verified, and Vera emits Wasm.
- For AI-written code, the TypeScript angle joins A: agents already write most new TypeScript, strictness is enforced only by convention (agent "skills"), and no study measures how often agents reach for `any` or `as`. Measuring that is itself an open, publishable gap close to the author's work.

### Gaps

- I found no study of `any`/`as` frequency in AI-generated TypeScript.
- The 633-report study's breakdown by cast or `any` was not readable (arXiv was blocked).
- I could not check whether TypeScript 7 changed any soundness-relevant defaults.
- Valibot, ArkType and Effect download figures are single-source.
- I found no evidence of a verified language publishing typed npm packages at scale.

## Which compile targets and host ecosystems give a new language the fastest adoption in 2026?

### Takeaway
Riding a host ecosystem is the dominant pattern: Kotlin/JVM and Android, TypeScript/JS, Gleam on BEAM and JS, Swift on iOS, Zig through `zig cc`. The 2026 evidence adds that Python wheels (PyO3/maturin) and JS/Wasm bindings (wasm-bindgen) are now huge distribution channels in their own right. Ruff ships Rust inside a Python wheel, and the GPU DSLs and Mojo ship on PyPI. TypeScript/npm is the largest audience, and agent tooling is converging on it (for example, the Bun acquisition). The WASI component model is promising but pre-1.0.

  3. Wasm (via wasm-bindgen for the browser, and the component model once WASI 1.0 lands);
  4. JVM (strong only with a sponsor, as with Kotlin/JetBrains/Google);
  5. C ABI (universal but brings no audience; Zig won through `zig cc`, not through ABI output).

## Can LLMs write a brand-new language well, given a spec, examples and compiler feedback?

### Takeaway
Partly yes, with feedback. Self-reported results (Vera) claim frontier models write a never-seen language at or above their Python accuracy on small problems, and Nanolang and Rue show agents producing working code or even compilers once given examples and a feedback loop. Controlled evidence shows a large cold-start penalty when the language is low-resource or complex (Dafny 82% vs Verus 44% vs Lean 27%; hallucinated Pallas APIs). It also shows that type-constrained decoding and verifier feedback close much of the gap. Independent, peer-reviewed evaluation of any brand-new language is missing.

### Cited Findings
- **Vera (self-reported)**: Kimi K2.5 scored 100% on 50 Vera problems, against 86% in Python and 91% in TypeScript. UNVERIFIED — [veralang.dev](https://veralang.dev/); [Negroni blog](https://negroniventurestudios.com/2026/04/13/language-design-doing-the-heavy-lifting/). Earlier notes record VeraBench as 60 problems, with six of nine models at 100%. NOTES (`frontier_pl_research.md`). **Conflict** on the problem count. Not peer-reviewed.
- **Nanolang**: in a demo, a model first produced non-compiling code, then a working Mandelbrot CLI once given examples and run in an agent loop. NOTES (`ai_code_generation.md`)
- **Rue**: an agent built "core basics of a language + spec with two different codegen backends... in roughly a week". Later autonomous work produced 95 merged PRs, but the test suite had been "lying" and ownership was unsound in the binary. NOTES (`new_languages_adoption.md`)
- **Cold-start penalty**: vericoding success is 82.2% in Dafny, 44.2% in Verus and 26.8% in Lean. SNIPPET-CONFIRMED (see A). Models "routinely hallucinate Pallas APIs". NOTES (`performance_and_gpu.md`). A June 2026 paper treats Gleam and MoonBit as "no-resource" languages. NOTES; numbers not obtained — [arXiv 2606.16827](https://arxiv.org/abs/2606.16827)
- **Feedback and constraints help**: type-constrained decoding cuts compile errors by more than half and repairs 37% more non-compiling code (PLDI 2025). MoonBit builds local and global constrained sampling into its toolchain. AlphaVerus bootstraps Verus from Dafny by translation. NOTES (`ai_code_generation.md`). AutoVerus solves more than 90% of 150 tasks with verifier feedback. CONFIRMED (see A).
- **Specs are the weak point**: LLMs weaken specs to make a verifier pass. NOTES (`HANDOFF.md`, SepInfer). At repository scale, agents break existing proofs when rewriting code (Vero). UNVERIFIED (see A).

### Inferences
- A new language designed for agents can get past the cold start if it (a) is close to a high-resource language in syntax, (b) gives structured, machine-readable diagnostics (Zero's JSON repair plans), and (c) supplies examples and a spec in context. The self-reported Vera numbers are consistent with this but prove nothing on their own.
- The bigger risk is not whether models can write the language but whether they can game the checker. Any verification-first design needs contracts that the agent cannot edit, and review of the contracts themselves.

### Gaps
- Not re-searched this session (search budget exhausted): independent evaluations of in-context learning of unseen languages, and 2026 constrained-decoding results. VeraBench's methodology could not be read.

## Comparison across candidates, and the strongest evidence for and against each

### Takeaway
A (verification-first for AI code) and E (the TypeScript angle) have the most demand evidence and fit the author's skills best (separation logic, symbolic execution, Lean, TypeScript AST tooling). A is also the most crowded and best funded. B has the least competition but a structural problem: it cannot protect the existing dependencies where attacks happen. C and D are dominated by vendors or big-language sponsors. A combination of A and E (a contract-checked language that emits TypeScript for npm, with contracts the agent cannot weaken) is the one position no competitor found in this session occupies. That is an inference, not a finding. The report writer should weigh it against the risks listed.

### Strongest evidence for and against each

- **A. For:** real industrial wins (AWS Dafny; SymCrypt in Windows Insider builds); LLMs are already good at proofs when given a spec (Dafny 68%→96% in a year; AutoVerus >90%); heavy investor demand (Axiom $200M). **Against:** crowded, with funded rivals launching in 2026 (Bend 2, Zero, MoonBit, CodeSpeak, Tessl); new languages start at a cold-start penalty (Verus 44% and Lean 27% vs Dafny 82%); agents weaken specs (SepInfer) and break proofs at repository scale (Vero); purpose-built agent languages have hundreds of stars, not users.
- **B. For:** attacks are growing (Axios, TeamPCP, a vendor-reported 2.6x increase in campaigns); no mainstream runtime has per-dependency least privilege, and Node says its model does not stop malicious code; almost no active language competitor (Austral dormant). **Against:** a new language protects only its own code, not the npm/PyPI dependencies that are attacked; the ecosystem is moving to install-time controls (pnpm v11) and runtime compartments (LavaMoat, WASI) instead; past attempts stalled.
- **C. For:** a clear technical gap (no race-safe portable kernel language); Python wheels make distribution easy. **Against:** NVIDIA, Qualcomm/Modular and OpenAI dominate; hardware changes every generation; LLMs hallucinate low-resource DSLs.
- **D. For:** memory safety remains a policy priority, and research on modes and value semantics is award-winning. **Against:** Swift ships the features with Apple's backing, Rust keeps absorbing verification tools, and independent efforts (Vale, Austral, Hylo) stalled.
- **E. For:** the largest host ecosystem (TS #1 on GitHub); a real 2026 security CVE caused by trusting erased types (n8n); the author's own results show soundness cannot be retrofitted (94.7% of `as unknown as` unrefutable); runtime-validator demand is huge (Zod ~212M/week). **Against:** type errors are only 12.4% of TS bugs in the 2026 study; every sound TS alternative has stayed niche or closed (Flow, Hegel, ReScript); TS 7 improves speed, not soundness, and the TC39 path is stalled; no data shows AI agents make casts worse.

### Inferences
- The candidates are not exclusive. A (contracts and SMT), B (capability or effect signatures) and E (TypeScript output) can be one design: contract and effect signatures as the human review surface, checked in seconds, compiled to TypeScript with runtime guards at the untyped boundary, and with a floor guard that stops agents from weakening contracts. That design meets the most evidence *for* in A, B and E. It still faces the main *against* items: a funded, crowded category, the cold-start penalty, and weak measured bug cost for TypeScript casts.
