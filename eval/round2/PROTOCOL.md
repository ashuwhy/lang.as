# Agent evaluation, round 2: protocol (pre-registered)

Written and committed on 2026-10-01, before any round 2 agent run, the pilot included. Changes
after this commit go in the list at the end with their date and reason; nothing above that list
is edited.

## Question

Round 1 hit a ceiling: 0 of 36 Touchmark runs and 0 of 36 Rust runs shipped a defect, so it could
not say whether Touchmark cuts escaped defects. Round 2 asks the same question on tasks where
agents writing Rust do ship bugs: when a frontier coding agent implements the same hard,
multi-function problem in Touchmark and in Rust, which language's solutions fail fewer hidden
tests, and at what token cost?

## What changed since round 1

Three compiler and reference commits, all before this protocol:

- `5275074`: from the round 1 findings, O(n) run-time sortedness checks and caller-side proofs
  of sortedness, `sum` in contracts, `i128`, and modulo by a variable in contracts.
- `53499eb`: a shorter reference (`llms.txt`, 3,225 to 2,688 o200k tokens) that tells agents to
  state the specification as `ensures` and let the proof replace tests.
- `93df923`: a fix to contract inference, found while I wrote the round 2 gold solutions (below).

No language feature was added for the round 2 tasks.

21 Hard problems, of which 10 drop out for taking strings (3) or two-dimensional arrays (7),

## Hidden tests and scoring

Each task has 19 to 22 hidden tests (223 in all): the published examples, edge cases at the
bounds of the domain, seeded random literal inputs, and five or six inputs of the largest allowed
size. Arrays longer than a few hundred elements are not literals: a test names a generator (`gen.py`, a 31-bit LCG with seven
shapes such as sorted, runs, distinct, triangle wave and multiples) that the test program expands
in its own language, with identical values in Python, Rust and Touchmark. In Touchmark the
generator is a `pub fn` whose `ensures` give the length, the value range and, where the domain
requires it, distinctness, so the caller-side proof sees exactly the stated domain.

Expected values come from Python reference implementations (`refs.py`). Each is checked against a
brute-force definition of the problem on random small inputs (300 per task per seed) and against
the published examples (`check_refs.py`), and every hidden test is checked to lie inside its stated
domain (`check_domain.py`: 0 of 240 outside, pilot included).

The scorer (`harness.py`) appends a `main` that calls the agent's function on every test in turn
and prints the results, builds it (`tmk build`, which verifies first, or `rustc -O`), and runs it
under a pseudo-terminal so that each output line has a timestamp. A test passes when its output
matches and it took at most 1.0 s of wall time. A test with no output for 10 s is stopped, and a
crash or a stop costs only that test: the remaining tests go on in a new program. A test that was
stopped or took over 1.0 s is re-run once on its own, and the re-run decides. A build that fails,
or takes over 900 s, fails every test of the run, as does a missing solution file.

A Touchmark test program verifies the agent's code again, next to the generators and `main`.
Inference for a private function draws up to 20 constants from its own body first and then from
the rest of the module, so a solution with few constants of its own also sees the generators'.
When a Touchmark test program fails to build, the scorer also runs `tmk check` on the solution
file alone and records the answer. Such a run counts as defective in every outcome below, as a
user would see it; the standalone answers are reported next to it.

Before any agent ran, I wrote a solution to every task in both languages. All 22 pass all 223
hidden tests, and the pilot's two pass its 17. The slowest single test took 0.148 s in Rust
(`shadow_pairs`) and 0.096 s in Touchmark (`shadow_pairs`). Every Touchmark gold verifies with
0 checks kept at run time.

The tests, references, generator, scorer, gold solutions and the audit below stay outside the

## Runs

Three independent runs per task and language, 66 counted runs, plus the pilot in each language.
Every run gets a fresh, empty `/work/<run-id>/` and a fresh sub-agent. Start order:

1. **Pilot**: `max_valid_pair_sum` in Rust and Touchmark. It checks the prompts, the scorer and
   the token and access audit; its numbers are reported separately.
2. **Rust calibration**: trial 1 of the 11 tasks in Rust. **Stop rule**: if 0 or 1 of these 11
   runs is defective, round 2 stops there and reports the calibration alone, because the tasks
   would again be too easy for the defect question (with 33 runs an arm, even 3 Rust defects
   against 0 gives Fisher p = 0.24). The calibration runs count as Rust trial 1 if the round goes
   on.
3. **Touchmark trial 1** on the 11 tasks.
4. **Trials 2 and 3**, task by task, the language order alternating between tasks and trials.

At most four agents run at once, started in this order. Wall times are therefore affected by
the load and are reported only as a secondary measure.

A run cut off by a usage or session limit (the transcript ends in a limit error, with no final
answer) is re-run with a fresh agent and directory; the cut-off agent's ID is kept and nothing
from it is scored. Any run that ends for another reason counts as it is.

The agents start in the repository root. While they run, the private directory, the compiler
worktree and `eval/` are mode 000. The audit (`usage.py`) lists every absolute path in an agent's
tool calls outside its directory and the reference, plus markers of the repository, the private
directory, the older `tmk` build in `/usr/local/bin` (which a login shell would find before the
round 2 build) and login shells. A run with a flagged path is examined by hand and reported, and
if it read anything that could help, it is re-run.

## Outcomes and analysis

- **Primary**: the share of runs with at least one escaped defect, meaning any hidden test that
  does not pass (wrong answer, crash, time over the limit, build failure, missing file), Touchmark
  against Rust over the 33 runs of each, with Fisher's exact test (two-sided). Reported with the
  counts, not only the p-value.
- **Stratified**: the same comparison with tasks as strata, by the exact conditional test of a
  common odds ratio of 1: under the null, Touchmark's defective count in each task is
  hypergeometric given that task's margins, the total is their convolution, and the two-sided
  p-value sums the probabilities no larger than the observed total's.
- **Secondary**:
  - correctness only, counting wrong answers, crashes, build failures and missing files but
    not time;
  - the share of hidden tests passed;
  - tokens per run, as in round 1: T_ctx (the conversation at the last model call), T_proc (prompt
    tokens summed over all calls) and T_work (T_ctx minus the first call's prompt), with a
    breakdown by cause;
  - tool calls and wall time;
  - the final solution's size in o200k tokens;
  - for Touchmark, the checks the final solution keeps at run time;
  - runs that answered DONE with a solution that does not build.
- Per-task tables for everything, and every solution committed.

**Decision rules**, fixed now:

- **Fewer defects**: Touchmark has fewer escaped defects when its defective runs number at most
  half of Rust's and the pooled Fisher p is below 0.05. If Touchmark has more defective runs with
  p < 0.05, that is reported as Touchmark worse. Anything else is no difference shown, and I will
  say so in those words.
- **Tokens**: the ratio of summed T_work, Touchmark over Rust, over all counted runs. The design
  document's stop rule is more than twice Rust's tokens after two rounds of documentation and
  diagnostic fixes. This round comes after the first such round, so a ratio above 2.0 here
  requires one more round of fixes, and the rule is judged at round 3.

For scale: with 33 runs an arm, Fisher's two-sided p falls below 0.05 at 8 against 1 (0.027), 6
against 0 (0.024) and 12 against 4 (0.042), but not at 6 against 1 (0.10) or 5 against 0 (0.053).

Whatever the result, it goes into `eval/round2/RESULTS.md` and the README in the same words.

## Known asymmetries and risks

- I chose the selection rule, wrote the specifications, the tests and the references, and I
  designed the language. The rule fixes the problems; the wording and tests are mine.
- Touchmark has no sort, maps, bit operations or nested arrays. Several tasks want one of them
  (`widest_fence`, `elevator_penalty` and `shadow_pairs` want sorting; `largest_power` wants bit
  operations; `max_valid_splits` wants a sparse table in Rust's usual solution), so Touchmark
  agents must write a merge sort or digit arithmetic themselves. That is a real cost of the
  language today, not something to correct for.
- Models have seen far more Rust than Touchmark, whose only documentation is the 2,688-token
  reference.
- A Touchmark test program re-verifies the agent's code in a larger module (see scoring), and
  scoring a Touchmark gold took 10 to 96 s, mostly verification; a solution that verifies slowly
  may pass its own checks and still exceed the 900 s build limit.
- My global instructions for the agent runner are in every sub-agent's context, in both arms.
- Runs are concurrent, at most four at a time, so wall times and any timing the agents measure
  themselves are noisier than in round 1.

## What writing the gold solutions found

- **A hidden test outside its domain.** A `widest_fence` test had a plank of height
  2 * 10^9 - 1, above the stated maximum of 10^9. The Rust gold passed it. The Touchmark gold
  failed to build, because the call in the test program broke the function's `requires`
  (E0203). I fixed the test (now 10^9 - 1) and added `check_domain.py`, which checks every test
  against its domain.
- **A compiler bug.** Contract inference for private functions dropped true preconditions when a
  slow caller used up the shared time budget, after which a helper (`gap` in the elevator gold)
  could not be proved free of overflow. Fixed in `93df923`, with a regression test: unanswered
  candidates get more passes, with a short time limit each, for as long as each pass answers
  some. The compiler's test suite passes with it.
- The test programs' generators are now `pub`, so their contracts are taken as written instead of
  being inferred, which saved 6 to 13 s of verification per generated input.
