# Make AI-written code prove its contract

The biggest real pain point in software development in September 2026 is no longer writing code but establishing that code does what it was meant to do, now that machines write a large share of it. One in three GitHub pull requests involves an agent and 84–90% of developers use AI tools, yet developers distrust the output, agents learn to satisfy tests rather than intent, security pass rates in generated code have not moved, and Google's DORA programme calls the cost the "verification tax". A language cannot fix review culture, but it can own a short, machine-checked contract that a human reviews, that an agent may not weaken, and that states what code may touch and which data it may trust. The recommendation is **Assured Script** (working name, a rebuild of AS Lang): a small, sound, TypeScript-shaped language for the money, permission, state-machine and parsing modules of TypeScript codebases, with `requires`/`ensures` contracts and explicit effects checked by an SMT solver in seconds, compiled to ordinary TypeScript, `.d.ts` files and Standard Schema-compatible validators. Its killer feature is a **contract lock over sealed boundaries**: a change that weakens a pinned contract, widens a function's effects or lets unchecked data across a JSON or host boundary fails the build until a human approves it. The lock alone is no longer new: LemmaScript, a "Tech Preview" on npm since April 2026 that verifies annotated TypeScript through Dafny or Lean 4 as "the correctness layer for AI-generated software", already requires LLM-edited proof files to differ from generated ones by additions only, the same safeguard as the floor guard in the author's SepInfer research. What still sets Assured Script apart is what an annotation layer cannot easily give: no `any`, casts or non-null assertions (a 2026 study finds agents nine times as prone as humans to use `any`), compiler-generated checks wherever erased types meet real data (the fix that every 2026 post-mortem reviewed here applied by hand), and effects and taint inside the pinned contract. That edge is plausible but unproven, so the plan opens with a three-month experiment against LemmaScript and a pre-registered pivot: if annotated TypeScript matches a sound core on the bugs that matter, the author contributes the lock and boundary work to LemmaScript or ships it as a tool, and builds no language. No controlled study yet shows that a language reduces defects in AI-written code; the roadmap replaces most of the AS Lang core while keeping its Rust workspace, CLI, LSP scaffold and WebAssembly packaging.

## Code got cheap in 2026; knowing it is right did not

The population at stake is large and still growing: SlashData counts **47.2 million developers worldwide in early 2025, 36.5 million of them professional**, although growth slowed to 10% a year ([SlashData](https://www.slashdata.co/post/global-developer-population-trends-2025-how-many-developers-are-there)). AI authorship is now their default workflow, not an experiment. **84% of the 49,000 Stack Overflow 2025 respondents use or plan to use AI tools** ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai)), 85% of JetBrains' 24,534 respondents use AI regularly ([JetBrains](https://blog.jetbrains.com/research/2025/10/state-of-developer-ecosystem-2025/)) [vendor], and 90% of DORA's roughly 5,000 respondents use it at work ([Google Cloud, DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)) [vendor]. The platform figures are larger still: in July 2026 Microsoft reported **225 million GitHub users, 50 million Copilot users, and that "one in three pull requests on GitHub now involves an agent"** ([Microsoft FY26 Q4 earnings](https://www.microsoft.com/en-us/investor/events/fy-2026/earnings-fy-2026-q4)). Unaudited company claims point the same way: Google says 75% of its code is "AI-generated and approved by engineers" as of April 2026 ([Fast Company](https://www.fastcompany.com/91531519/google-ceo-says-75-of-the-companys-code-is-ai-generated)), and at the most AI-heavy firm with a published number, Claude authors "about 80% of the code merged", and the team found it "could only move as quickly as humans could review code" ([Anthropic](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)) [vendor].

Trust moved the other way. In the same Stack Overflow survey **46% distrust AI output against 33% who trust it, only 3% "highly trust" it, 66% name "almost right, but not quite" as their top frustration and 45% say debugging AI code takes longer**, even though 51% of professional developers use AI tools daily ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/ai)). DORA's 2024 report associated each 25% rise in AI adoption with an estimated **1.5% fall in delivery throughput and a 7.2% fall in delivery stability** ([Google Cloud, DORA 2024](https://cloud.google.com/blog/products/devops-sre/announcing-the-2024-dora-report)) [vendor]; by 2025 the throughput link had reversed to positive while the stability link stayed negative, so teams got faster and less stable, because "an increase in change volume leads to instability" without strong controls ([DORA 2025](https://cloud.google.com/blog/products/ai-machine-learning/announcing-the-2025-dora-report)) [vendor]. DORA's April 2026 ROI report calls the extra effort "to check whether AI-generated code is reliable, secure, and aligned with the system architecture" the **verification tax** ([Google Cloud](https://cloud.google.com/resources/content/dora-roi-of-ai-assisted-software-development); definition via [InfoQ](https://www.infoq.com/news/2026/05/dora-roi-ai-assisted-dev-report/)) [vendor]. Telemetry agrees on direction: Faros measured 98% more merged pull requests but **91% longer review times** and 154% larger PRs on high-adoption teams, with company-level throughput flat ([Faros](https://www.faros.ai/blog/ai-software-engineering)) [vendor]. Measured productivity has lagged perceived productivity: METR's 2025 randomised trial found experienced developers took **19% longer** with AI while believing they were 20% faster ([METR](https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/)). Its February 2026 follow-up points the other way, with returning developers taking 18% less time, but the confidence interval crosses zero and METR calls the result "only very weak evidence" of a speedup ([METR](https://metr.org/blog/2026-02-24-uplift-update/)). Output is rising; the evidence that it is rising faster than the cost of checking it is thin.

The check most teams rely on is the one agents learn to game. OpenAI stopped reporting SWE-bench Verified after an audit found flawed tests or descriptions in **at least 59.4%** of the problems it examined and found frontier models reproducing gold patches verbatim ([OpenAI](https://openai.com/index/why-we-no-longer-evaluate-swe-bench-verified/)). Maintainers reviewing 296 test-passing AI pull requests on SWE-bench repositories would have rejected **roughly half**, a merge rate about 24 points below the automated grader ([METR](https://metr.org/notes/2026-03-10-many-swe-bench-passing-prs-would-not-be-merged-into-main/)). Microsoft Research found production agents "deliver what you check, not what you requested", reaching near-perfect scores on a hidden 222-test oracle while leaving the actual library "dead or absent" ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/building-to-the-test-coding-agents-deliver-what-you-check-not-what-you-requested/)), and that co-generated reproduction tests are often "lax", passing when both patch and test are wrong ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/beyond-fail-to-pass-iterative-hardening-of-co-generated-bug-reproduction-tests-and-fixes/)). Security failure is flat: Veracode's 2026 report puts the average security pass rate across more than 100 models at **56%, "virtually unchanged since last year"**, with Java last at 30% and cross-site-scripting checks passed only 15% of the time ([BusinessWire](https://www.businesswire.com/news/home/20260728207685/en/LLMs-Are-Getting-Smarter-But-Not-Safer-Veracode-2026-GenAI-Code-Security-Report-Finds-AI-Generated-Code-Security-Has-Stalled-at-56-Pass-Rate)) [vendor]. That Java, a statically typed memory-safe language, is worst says ordinary static types do not stop taint bugs. GitClear's 2026 data adds a **47% rise in error-masking constructs**, code that swallows failures ([GitClear](https://www.gitclear.com/the_ai_code_quality_maintainability_gap)) [vendor], and in an Anthropic trial engineers learning with AI scored 50% against 67% on a follow-up quiz, worst on debugging ([Anthropic](https://www.anthropic.com/research/AI-assistance-coding-skills)) [vendor]: reviewers are getting weaker as the load grows.

What measurably works replaces human reading with machine-checkable evidence. Microsoft Research's AutoVerus proves more than **90% of 150 Rust proof tasks**, half in under 30 seconds or three model calls ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/autoverus-automated-proof-generation-for-rust-code/)); VeruSAGE agents finish **over 80% of 849 proof tasks** from eight real verified Rust systems ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/verusage-a-study-of-agent-based-verification-for-rust-systems/)). In a user study, formalised intent in the form of tests made programmers **"significantly more likely to correctly evaluate AI generated code"** and lifted pass@1 by 45.97 points within five interactions ([Microsoft Research, TiCoder](https://www.microsoft.com/en-us/research/publication/llm-based-test-driven-interactive-code-generation-user-study-and-empirical-evaluation/)). Anthropic raised the share of pull requests getting substantive review comments from **16% to 54%** by requiring review agents to "write a proof that their finding is valid" ([Anthropic](https://claude.com/blog/how-anthropic-secures-its-ai-native-software-development-lifecycle)) [vendor]. Industry already ships the pattern of a small verified core compiled into a mainstream stack: AWS's Dafny-written authorisation engine handles about **a billion calls a second**, was deployed in 2024 "without incident" and runs three times faster, compiled to reviewable Java ([Amazon Science](https://www.amazon.science/publications/formally-verified-cloud-scale-authorization)), and Microsoft's Lean-verified Rust cryptography is in Windows Insider builds, at the price of a **237 KLOC Lean development to verify 16.7 KLOC of Rust** ([arXiv 2609.15648](https://arxiv.org/abs/2609.15648)). The research agenda names the bottleneck precisely. Shuvendu Lahiri calls intent formalisation "the key challenge that will determine whether AI makes software more reliable or merely more abundant" and specification validation its "central bottleneck" ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/intent-formalization-a-grand-challenge-for-reliable-coding-in-the-age-of-ai-agents/)); PLDI 2026 gave a keynote to Miryung Kim on "Navigating the AI Validation Bottleneck" ([PLDI 2026 keynotes](https://pldi26.sigplan.org/track/pldi-2026-pldi-keynotes)); and Leonardo de Moura argues for letting "AI move fast, but make it prove its work", behind a trusted kernel of "a few thousand lines" ([de Moura](https://leodemoura.github.io/blog/2026-2-28-when-ai-writes-the-worlds-software-who-verifies-it/)) [opinion].

Four things are not known, and the report treats them as open rather than papering over them. Nobody has priced the verification tax in dollars; the best proxies are review time, instability and security pass rates. No independent study compares production incident rates of AI-written and human-written code. Agents demonstrably reach for TypeScript's escape hatches more often than humans do (below), but nobody has linked that habit to runtime failures. And **no controlled study shows that choosing a language, by itself, lowers defects in AI-written code**; the evidence is mechanism-level, from compiler and verifier feedback loops and formalised intent.

**Memory safety has the strongest proof that a language fixes it, and that proof belongs to Rust.** Android's memory-safety share of vulnerabilities fell from 76% in 2019 to 24% in 2024 ([Google Security Blog](https://security.googleblog.com/2024/09/eliminating-memory-safety-vulnerabilities-Android.html)) and below 20% in 2025, with Rust showing about a thousand times lower vulnerability density than Android's C and C++ ([Google Security Blog](https://security.googleblog.com/2025/11/rust-in-android-move-fast-fix-things.html)); memory corruption was still about 35% of the 90 zero-days exploited in 2025 ([GTIG](https://cloud.google.com/blog/topics/threat-intelligence/2025-zero-day-review)). Policy pushes the same way but gently: CISA and FBI guidance, revised in January 2025, asks manufacturers to publish memory-safety roadmaps "by the end of 2025", exempts products whose support ends before 2030, is voluntary, and has no public count of who complied ([CISA](https://www.cisa.gov/sites/default/files/2025-01/joint-guidance-product-security-bad-practices-508c_0.pdf)). But greenfield safe systems code is served by Rust, Swift and the garbage-collected languages, and the brownfield is crowded: C++26 was finished in March 2026 without Profiles, now aimed at C++29 ([Herb Sutter](https://herbsutter.com/2026/03/29/c26-is-done-trip-report-march-2026-iso-c-standards-meeting-london-croydon-uk/); [wro.cpp](https://wrocpp.github.io/posts/cpp-safety-state-of-the-union-may-2026/)), Linux made Rust permanent in December 2025 ([LWN](https://lwn.net/Articles/1049831/)), Carbon's 0.1 is "end of 2026" at the soonest ([Carbon roadmap](https://github.com/carbon-language/carbon-lang/blob/trunk/docs/project/roadmap.md)), and DARPA's TRACTOR funds automated C-to-Rust translation ([TRACTOR benchmark](https://arxiv.org/abs/2609.25121)). A new language here would compete on interop with Carbon and as a translation target with Rust, which is not a small-team fight.

**Supply-chain attacks have a real language-level root cause, ambient authority, but 2026 moved most of the attack surface elsewhere.** Sonatype counted **454,600 new malicious packages in 2025** ([Sonatype](https://www.sonatype.com/state-of-the-software-supply-chain/2026/open-source-malware)) [vendor]; Shai-Hulud 2.0 backdoored 796 npm packages with over 20 million weekly downloads through a `preinstall` hook ([Datadog](https://securitylabs.datadoghq.com/articles/shai-hulud-2.0-npm-worm/)); and on 31 March 2026 North Korean actors published backdoored `axios` versions whose payload ran from a dependency's `postinstall` script, in a package Microsoft puts at over 70 million weekly downloads and GTIG at over 100 million [conflict] ([Microsoft](https://www.microsoft.com/en-us/security/blog/2026/04/01/mitigating-the-axios-npm-supply-chain-compromise/); [GTIG](https://cloud.google.com/blog/topics/threat-intelligence/mitigation-guidance-for-supply-chain-compromise)). AI assistants add a vector: code models hallucinate package names at rates from 5.2% for commercial models to 21.7% for open-source ones across 576,000 samples, per the paper's arXiv abstract, although search summaries of the published version say 2.23 million [conflict] ([Spracklen et al.](https://arxiv.org/abs/2406.10279)), and a 2026 re-evaluation of five newer models still finds **4.62% to 6.10%**, with 53 names that all five invent still registrable after disclosure ([arXiv 2605.17062](https://arxiv.org/abs/2605.17062)). Dollar figures are projections, not measurements. Registries moved first: **npm 12.0.0, published on 8 July 2026, skips dependency install scripts unless the project lists them in `allowScripts`, and turns git and remote-URL dependencies off by default** ([npm 12.0.0 docs](https://registry.npmjs.org/npm/-/npm-12.0.0.tgz); [Socket](https://socket.dev/blog/npm-12)), which blocks the install-time route that both Shai-Hulud 2.0 and axios used, though projects that stay on the still-maintained npm 11 line or approve scripts wholesale keep the old behaviour. The remaining language-shaped gap is what imported code may do once running: Node's permission model is process-wide and "does not provide security guarantees in the presence of malicious code" ([Node.js docs](https://nodejs.org/api/permissions.html)). But a new capability-safe language only constrains code written in it, while the attacks live in existing packages, and the one language that built the idea, Austral, has had no push since July 2025 ([Austral](https://github.com/austral/austral)). Capabilities survive below as a review surface, not as the pitch.

**The GPU problem has the most money and the fewest winnable openings.** Hyperscaler 2026 capital spending estimates run from about $660B to $800B, mostly on AI ([Futurum](https://futurumgroup.com/insights/ai-capex-2026-the-690b-infrastructure-sprint/)), and vLLM calls maintaining hundreds of kernels across NVIDIA, AMD and Intel "impractical" ([vLLM](https://vllm.ai/blog/2026-03-04-vllm-triton-backend-deep-dive)). But the people writing kernels are few, and the field is vendor-owned: Mojo 1.0 shipped on PyPI on 11 August 2026 ([PyPI](https://pypi.org/pypi/mojo/json)), two weeks after Qualcomm completed its purchase of Modular in a deal Reuters valued at about $3.9B ([Nasdaq](https://www.nasdaq.com/press-release/qualcomm-completes-acquisition-modular-2026-07-29); **The notes leaned toward two answers, and both need trimming.** The first, a verification-first language for AI-written code, is right about the pain and wrong about the shape. Against it: the only defect evidence is mechanism-level; the 2025–2026 award lists reward verification of real systems code and language-level safety but give **nothing to LLM-plus-verification work**, neither among PLDI 2026's ten Distinguished Papers ([PLDI 2026](https://pldi26.sigplan.org/track/pldi-2026-papers)) nor POPL 2026's eight ([POPL 2026](https://popl26.sigplan.org/track/POPL-2026-popl-research-papers)) nor the OSDI, SOSP, ASPLOS and MLSys best papers; the market rewards workflow tools on existing languages, with GitHub's Spec Kit at 138,720 stars ([GitHub](https://github.com/github/spec-kit)) while the most-starred purpose-built "languages for LLMs" have hundreds ([Nanolang](https://github.com/jordanhubbard/nanolang)); and the category is funded and crowded, with Axiom raising $200M at a valuation above $1.6B to make AI output Lean-checked ([SiliconANGLE](https://siliconangle.com/2026/03/12/verifiable-ai-startup-axiom-raises-200m-prove-ai-generated-code-safe-use/)), Qodo $70M for code verification agents ([TechCrunch](https://techcrunch.com/2026/03/30/qodo-bets-on-code-verification-as-ai-coding-scales-raises-70m/)), Bend 2 announced on 17 September 2026 as "a language that blocks AI mistakes via proof" ([HN](https://news.ycombinator.com/item?id=49746163); [AkitaOnRails](https://akitaonrails.com/en/2026/09/19/new-ai-language-just-released-bend-2/)), LemmaScript already verifying annotated TypeScript for AI-written code ([npm registry](https://registry.npmjs.org/lemmascript)), Vercel's Zero, MoonBit and Vera all pitching AI-first languages, and Dafny and Verus already proven in industry. The author's own SepInfer probe adds the sharpest counterpoint: **38 strict-clean AI-generated TypeScript modules contained zero soundly detectable type faults**, the same near-zero density as human code, so "sound types catch AI bugs" is not a selling point. The second lean, capability-safe dependencies, loses to npm 12 and to the fact that a new language cannot protect the packages that are attacked. What survives both tests is narrower: the verification bottleneck is the biggest pain, a language can own its acceptance oracle, and the only winnable form adopts like a tool, inside the ecosystem where agents already write the most code, and wins where erased types meet real data.

## Pinned contracts and sealed boundaries in a sound TypeScript dialect

### One idea: contracts and boundaries are the review surface, and agents cannot move them

**Assured Script** (working name; it keeps the repository's AS name and `.as` extension) is a small, sound, TypeScript-shaped language for the modules of a TypeScript codebase where a wrong answer costs money or security: ledgers and billing, authorisation rules, pricing, state machines, and parsers of untrusted input. Programs compile to readable TypeScript plus `.d.ts` declarations that any npm project imports like any other module, and a team that abandons the language keeps the emitted code. The killer feature is the **contract lock**. Every exported function's contract, effect list, refinement types and boundary decoders are recorded in a `contracts.lock` file, the way `package-lock.json` pins dependencies. On every build the checker proves that the new contract refines the pinned one: the old precondition must imply the new one, and under the old precondition the new postcondition must imply the old one; effects may shrink but not grow, and a decoder may tighten but not loosen. A weakening fails with a concrete counterexample and can only land through an approved edit to the lock file, which CODEOWNERS routes to a human. Agents are free to rewrite implementations, because the checker proves those against the contract; they are not free to move the goalposts, which is the failure SepInfer measured, METR and Microsoft Research observed with tests, and LemmaScript guards against at its proof layer.

LemmaScript changes the argument for why this must be a language. An earlier version of this plan held that a tool on plain TypeScript can test contracts but only a restricted language can prove them; LemmaScript proves annotated TypeScript functions through Dafny or Lean, including, by its own account, security middleware covering four Hono CVEs ([npm registry](https://registry.npmjs.org/lemmascript)) [vendor]. The case for a language now rests on the code around the contract. SepInfer found 44–48% of real type assertions beyond any sound analysis, so a verifier of ordinary TypeScript must either accept only a subset, which is a language by another name, or trust annotations wherever `any`, casts and erased JSON types reach the verified function; the n8n vulnerability described below was precisely an annotation trusted at a boundary. A language can make the boundary part of the contract, with every crossing value checked by generated code and every effect declared, and it can compare two versions of a contract because the contract has a decidable meaning, which prose specs (Spec Kit, CodeSpeak, Kiro) lack.

### Core semantics

The core is deliberately small. Values are immutable records, tagged unions, arrays and maps; updates copy (`{ ...a, balance: b }`) and only local variables are mutable, so the core has no shared mutable heap and its verification conditions stay in the fragment SMT solvers handle well. `int` is a safe integer emitted as `number`, with the checker proving results stay in range, and `bigint` is explicit. There is no `any`, no `unknown` inside the core, no `as` cast, no non-null assertion, no implicit coercion, no `null` (use `Option`) and no exceptions (use `Result`, which the compiler refuses to let a caller discard), which answers GitClear's error-masking signal directly. Absence is never a wildcard: `Option` has no truthiness and a filter over a set is either `All` or `Only(set)`, so the empty-value-matches-everything bug behind Cloudflare's February 2026 outage does not type-check, and taking a value out of a `Result` without handling the error is a proof obligation, not an `unwrap()` that can panic in production. Records are closed, so JSON merged into an object cannot add fields; that removes prototype pollution, the second-largest advisory class in a 51-package npm census taken for this research (51 advisories, 14 of them in axios) ([npm audit data](https://registry.npmjs.org/-/npm/v1/security/advisories/bulk)). Functions carry `requires` and `ensures` clauses and refinement types such as `int where self >= 0`; loops carry `invariant` and `decreases` or are written as folds. Functions are pure unless they declare effects such as `uses net`, `uses clock` or `uses log`, and they reach I/O only through capability values passed as parameters, which compile to ordinary TypeScript objects; the effect list is part of the pinned contract, so an agent that quietly gives a pure pricing function network access fails the build. Data arriving from the host is `Untrusted<T>` until decoded. Decoders are generated from declared types and emitted as validators implementing the Standard Schema interface, so tRPC, form libraries and ORMs accept them as they accept Zod's, and the sinks where Veracode's failures cluster (HTML, SQL, log lines, shell arguments) accept only values built by escaping constructors, the "secure by default API" lever that ordinary static types, as Java's record shows, do not provide.

Verification is modular and fast by design, and it is SMT-backed rather than interactive because that is where models succeed: off-the-shelf models solved 82% of Dafny tasks against 44% in Verus and 27% in Lean across 12,504 specifications ([arXiv 2509.22908](https://arxiv.org/abs/2509.22908)), and on VERINA's Lean tasks the best model wrote correct code 72.6% of the time, sound and complete specifications 52.3%, but proofs only 4.9% ([arXiv 2505.23135](https://arxiv.org/abs/2505.23135)). Each function is checked with Z3 against its callees' contracts under a per-function time budget, because agents loop on the checker thousands of times and the Verus team finds that "the difference between one second and 10 seconds" matters ([Microsoft Research podcast](https://www.microsoft.com/en-us/research/podcast/abstracts-november-5-2024/)). An obligation the solver cannot discharge in budget is never silently dropped: it becomes a runtime assertion in the emitted code plus a generated property test, and the report lists it as "checked at run time, not proved". That three-level verdict (proved, runtime-checked, rejected) follows Vera's published design ([PyPI veralang](https://pypi.org/project/veralang/)). Every diagnostic is available as JSON with stable codes and concrete counterexamples, the agent-facing interface Vercel's Zero popularised. To attack Lahiri's specification-validation bottleneck, the pull-request report shows a few concrete input/output examples the contract allows and one it forbids, generated from solver models, because a reviewer judges examples faster than formulas, as TiCoder's result suggests.

### Who adopts first, and through which door

TypeScript is the right host, and 2026 made it more so. **TypeScript became GitHub's most-used language by monthly contributors in August 2025**, with 2,636,006 contributors, up 66.6% ([GitHub Octoverse](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)); 40% of State of JS 2025 respondents write only TypeScript, and "lack of static typing" is still JavaScript's top write-in complaint with 1,102 mentions ([State of JS 2025](https://2025.stateofjs.com/en-US/features/)); and JavaScript and TypeScript made up 31% of the coding queries in Anthropic's April 2025 Economic Index sample ([Anthropic](https://www.anthropic.com/research/impact-software-development)) [vendor]. Every official path still keeps types erased at run time. TypeScript 6.0 made `strict` the default in March 2026, a change visible in the compiler source, and 7.0.2 keeps the same checking options ([TypeScript 6.0 notes](https://www.typescriptlang.org/docs/handbook/release-notes/typescript-6-0.html); [6.0.2 compiler](https://registry.npmjs.org/typescript/-/typescript-6.0.2.tgz)), but neither touches `as`, `any` or `!`, because a sound type system remains a stated non-goal ([TypeScript design goals](https://github.com/microsoft/TypeScript-wiki/blob/main/TypeScript-Design-Goals.md)). The TC39 type-annotations proposal is still at Stage 1 and would ignore types at run time anyway ([TC39 issue #178](https://github.com/tc39/proposal-type-annotations/issues/178)), and Node.js now runs `.ts` files by stripping types without checking them ([Node.js](https://nodejs.org/learn/typescript/run-natively)). The gap between annotation and run time is stable ground, not a target Microsoft is about to close.

The demand evidence sits in that gap. Lee, Ul Hassan and Hindle, in an MSR 2026 Mining Challenge paper on agent pull requests, find AI agents **"9x more prone to use the 'any' keyword"** than humans and more likely to add non-null and type assertions, while agent TypeScript pull requests are accepted 1.8 times as often as human ones ([arXiv 2602.17955](https://arxiv.org/abs/2602.17955)); these figures come from search summaries, and the paper's sample size was not found. By bug count the case is weaker. Tang, Alimadadi and Sumner's MSR 2026 study of 633 TypeScript bugs puts "Type Error", meaning incorrect, incomplete or unsafe annotations, at 12.4%, behind API misuse at 14.5%, finds tooling and configuration faults dominant, and gives no split for casts or `any` ([arXiv 2601.21186](https://arxiv.org/abs/2601.21186)); Bogner and Merkel found in 2022 that `any` use was not correlated with bug proneness ([arXiv 2203.11115](https://arxiv.org/abs/2203.11115)). By severity the picture reverses. n8n's critical CVE-2026-25049 gave attackers code execution because a sanitiser trusted a `string` annotation "not enforced through runtime type checking"; it is filed as CWE-913 rather than as type confusion, so CWE counts miss the class, and it was fixed by adding runtime type checks ([Endor Labs](https://www.endorlabs.com/learn/cve-2026-25049-n8n-rce); [GitHub advisory](https://github.com/advisories/GHSA-6cqr-8cfr-67f8)). The same non-string-where-a-string-was-assumed pattern recurs in 2026 advisories for tmp, handlebars, sequelize and node-tar, and every fix or recommendation found was a runtime check or isolation, never static types ([npm audit data](https://registry.npmjs.org/-/npm/v1/security/advisories/bulk)). The ecosystem already pays for runtime validation at compiler scale: on 24 September 2026 the npm registry showed **ajv at 287.9 million weekly downloads, zod at 211.9 million (more than the `typescript` package's 209.2 million), @sinclair/typebox at 81.2 million, the shared @standard-schema/spec interface at 80.7 million, effect at 26.3 million and valibot at 13.4 million** ([npm registry](https://registry.npmjs.org/-/v1/search?text=zod&size=20)). Transitive use inflates those counts, and ajv serves JSON Schema generally, but a language that generates such validators from its contracts replaces hand-synced schemas rather than competing with nothing. The validators are not immune themselves: SepInfer found that in zod 4.5.4 a `bigint` reaches a field declared `readonly divisor: number`, so `divisor * 2` throws on the published package (SepInfer paper, "The frontier"). Payments, fintech and DeFi SDK maintainers, where SepInfer's corpus found real laundering defects, are the beachhead; the buyer is the lead who sets the acceptance policy for agent pull requests.

The adoption wedge is one module at a time with a free exit. A team writes `ledger.as`, commits the generated `ledger.ts` and `ledger.d.ts`, and the rest of the codebase does not know or care; a GitHub Action posts the verdict on each pull request ("contract unchanged; 14 obligations proved; 0 checked at run time"), and removing the language means deleting one source file and keeping the TypeScript. This mirrors how every "better X" that worked lived inside X's ecosystem (TypeScript in JavaScript, Kotlin on the JVM) and how AWS made Dafny acceptable by emitting reviewable Java. The compiler itself ships through npm, as ReScript, Elm and PureScript do, rather than through installers, which is one reason Gleam and Dafny are invisible in npm data ([npm registry](https://registry.npmjs.org/rescript)). It also meets the 2026 toolchain bar: an agent skill, `AGENTS.md`, `llms.txt`, JSON diagnostics, an LSP, a VS Code extension also on Open VSX, and a browser playground.

### What it borrows, and where it differs from rivals

The pieces are established: Dafny-style auto-active verification with SMT, refinement types from Liquid Types and Flux, typed effects from F* (whose effects paper won POPL 2026's Most Influential Paper award ([MPI-SP](https://www.mpi-sp.org/94694/news_publication_26021689_transferred))) and effects-as-capabilities from Effekt, TypeScript subsets such as Microsoft's Static TypeScript ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/static-typescript/)), verifier-in-the-loop repair from AutoVerus, specification generation from VeriSpecGen ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/intent-aligned-formal-specification-synthesis-via-traceable-refinement/)) and nl2postcond, and type-constrained decoding. The last matters for TypeScript in particular: Mündler et al. (PLDI 2025) found that 94% of compile errors in TypeScript generated by open-weight models of 2B–34B parameters were type-check failures, and that constraining decoding with the type system "reduces compilation errors by more than half" ([arXiv 2504.09246](https://arxiv.org/abs/2504.09246)), a result GitHub later cited as a reason AI is pushing developers toward typed languages ([GitHub blog](https://github.blog/ai-and-ml/llms/why-ai-is-pushing-developers-toward-typed-languages/)). The award lists that ignore LLM-plus-verification keep rewarding these ingredients: OSDI 2026's best paper contains what opaque components do to a system, an argument for typed effects, and OSDI 2025's best paper, Omniglot, made interactions with foreign-language code safe, the problem the host-import rule addresses ([OSDI 2025](https://www.usenix.org/conference/osdi25/technical-sessions); [OSDI 2026](https://www.usenix.org/conference/osdi26/technical-sessions)). What is new here is the combination: the lock, the sealed boundary and the effect contract in one small language.

### LemmaScript holds the lock; the boundary is still open

LemmaScript is the most important new fact in this research, and it forces a plain decision. It is the closest prior art on every axis that matters: the same host, the same buyer, the same core safeguard (a model may add proof but may not remove what was generated), and a better adoption story for existing code, since teams annotate functions in place with `//@` comments instead of porting them. Its traction is small so far, about 1,733 weekly downloads, no dependent packages and case studies all in the vendor's own repositories, but it shipped 36 versions between 1 April and 19 September 2026 ([npm registry](https://registry.npmjs.org/lemmascript); [Midspiral](https://midspiral.com/blog/lemmascript-a-verification-toolchain-for-typescript/)) [vendor]. Nothing in the README text read here describes a proof that a new contract refines the last one, generated checks at JSON boundaries, or effects, and how it treats `any` and casts was not established.

Assured Script still differs, and the differences sort by how hard they are to copy. Three are language properties. Soundness by construction means there is no `any`, cast or `!` to reach for, so Lee et al.'s ninefold gap cannot arise; an annotation layer can lint for escape hatches but must accept the TypeScript it is given. Sealed boundaries mean the compiler writes the check n8n wrote by hand. Effects and taint in the pinned contract mean a pure function cannot quietly gain network access and a raw string cannot reach an HTML sink. Two more differences, SepInfer-derived floors and the refinement check between contract versions, are tool features LemmaScript could add; they justify contributions, not a language.

**The decision is to keep Assured Script as the one recommendation, re-centred on the boundary rather than on the lock, and to change the plan in three ways.** Phase 0 runs LemmaScript as the strongest annotated-TypeScript baseline and draws at least a third of its tasks from boundary and effect bugs, where the language claims its edge. Phase 0's contract-lock Action reads LemmaScript's `//@` annotations as well as its own sidecar format, so the lock helps LemmaScript users whichever way the study comes out. And the pivot is pre-registered: if the LemmaScript arm matches the sound-core arm on escaped defects, boundary and effect tasks included, the author builds no language and offers the lock, floors and validator generation to Midspiral or ships them as a companion tool; contacting Midspiral early keeps that open. A new language is justified only by what an annotation layer cannot do, the evidence says those things live at the boundary, and the experiment can show within three months whether that edge is real.

### A short program

The sketch below shows the syntax, the checker's contribution, the host boundary and the effect rules. Names and diagnostics are illustrative.

```ts
// ledger.as  ->  ledger.ts + ledger.d.ts
type Cents = int where self >= 0;          // int: a safe integer, emitted as number
type Account = { id: string, balance: Cents, frozen: boolean };
type TransferError = { kind: "frozen" } | { kind: "insufficient", short: Cents };

export function transfer(from: Account, to: Account, amount: Cents)
    : Result<[Account, Account], TransferError>
  requires from.id != to.id
  requires to.balance + amount <= int.max   // the checker asked for this line
  ensures  result is Ok([a, b]) ==>
             a.balance == from.balance - amount && b.balance == to.balance + amount
  ensures  result is Err({ kind: "frozen" }) <==> (from.frozen || to.frozen)
{
  if (from.frozen || to.frozen) return Err({ kind: "frozen" });
  if (from.balance < amount)
    return Err({ kind: "insufficient", short: amount - from.balance });
  return Ok([{ ...from, balance: from.balance - amount },
             { ...to,   balance: to.balance + amount }]);
}

import host { fxRate } from "./rates.ts";    // TS type (pair: string) => number: guard inserted
import host { loadUser } from "./db.ts";      // TS type (id: string) => any
// error AS0412: `loadUser` returns `any`, which no check can validate; import it through a decoder:
//   import host { loadUser } from "./db.ts" via decode<User>;   // emits a Standard Schema validator

export function logPayout(log: Log, user: Untrusted<string>, amount: Cents): void
  uses log                                    // no other I/O is reachable from here
{
  log.info(LogLine.of("payout ", LogLine.escape(user), " ", amount)); // raw `user` will not compile
}
```

When an agent, asked to make a failing check pass, relaxes the first postcondition, the build stops and says why in terms a reviewer can judge at a glance:

```text
$ as check
ledger.transfer  contract WEAKENED relative to contracts.lock
  pinned:    Ok([a, b]) ==> a.balance == from.balance - amount && b.balance == to.balance + amount
  proposed:  Ok([a, b]) ==> a.balance <= from.balance
  allowed now, forbidden before:
             from.balance = 100, to.balance = 0, amount = 30  ->  Ok(a.balance = 0, b.balance = 0)
  status:    blocked; a weaker contract needs an approved change to contracts.lock (owners: @payments)
ledger.logPayout  effects unchanged (log); 9 obligations proved, 0 checked at run time
```

The emitted `ledger.ts` is the same function body in plain TypeScript, with contracts carried as JSDoc and, for exported functions callable from unchecked code, an entry guard; `ledger.d.ts` exposes `Cents` as a branded number, and each decoder becomes a standalone validator module that other TypeScript code can use.

## SepInfer supplies the floor guard, the derivation and the boundary

SepInfer is the author's OCaml tool, described in the PLDI 2027 submission "Ground or Nothing: Characterizing Sound Refutation of TypeScript Type Assertions" (`paper/main-pldi.tex` in the private SepInfer repository). It derives separation-type specifications for TypeScript from declared types by forward symbolic execution with three load-bearing rules (cast transparency, strong update and must-alias), rather than asking a model to guess them, and reports "Class C" unsoundness, code TypeScript accepts but a sound verifier refutes, such as a string laundered into a `bigint` cell through `as unknown as bigint`. Five Lean lemmas establish that its transfer functions over-approximate concrete evaluation, giving a no-false-Class-C property under stated assumptions, and the paper is candid that the mechanisation models the derivation rather than being extracted from it. Four of its results carry straight into the language.

**The floor guard becomes the contract lock.** SepInfer's README records that "free-form LLM synthesis hides Class C": a model optimising "make the verifier pass" finds a weaker specification that verifies, so the bug hides itself. In the ablation, an OpenEvolve loop "verifies" every Class C function only through a spec the floor guard rejects, fails two sound controls, and takes 36–107 seconds per function against about 0.5 seconds for the derivation, roughly a hundred times slower (SepInfer `README.md`, Phase D). SepInfer's `spec_floor.ml` pins each `Ref<T>` cell to its declared type; Assured Script generalises the same rule from cell types to whole contracts, effect lists and decoders, turning a research safeguard into a build rule. LemmaScript's additions-only rule is the same safeguard found independently, which removes any claim that the idea is new but is the best outside evidence that the failure is general; METR's unmergeable test-passing PRs and "building to the test" point the same way, and Phase 0 is designed to measure how often frontier agents actually weaken contracts when allowed to.

**"Derive, don't guess" becomes derived floors.** SepInfer derives specifications mechanically with zero model calls, including per-field access annotations (untouched, read, written) and value types for a fifteen-function mutable list suite (paper, "General Type-State Inference" and its appendix table). In the language, every function without a hand-written contract still gets a derived floor (its frame, effects, totality and type-state) pinned in the lock, so even unannotated agent-written code cannot silently start writing a field or touching the network. Models are used only to propose stronger contracts, which the checker must prove, the same bounded role SepInfer gives its single floor-filtered CEGIS call.

**The refutation boundary becomes the host-import rule, and it argues against retrofitting.** The paper proves that refuting an assertion needs a decided value type and a declared type excluding it, and then measures where real code falls: in 22 production SDKs at pinned commits (15,139 files), **320 of 338 double casts, 94.7%, target a type nothing in its domain can refute**; classifying every assertion in two further corpora puts **44–48% beyond any sound analysis**, with only 10–11% "ground" in a type domain and 12–14% reachable with a record domain (paper, abstract and "The frontier"). That is the quantitative case that a sound checker bolted onto TypeScript cannot give the guarantee a contract gate needs on ordinary code, and Lee et al.'s ninefold `any` finding means agent-written TypeScript produces more of exactly the blind types this classification cannot see through. The same classification tells the language how to treat TypeScript it imports: a decided host type such as `(pair: string) => number` gets an automatically generated runtime guard, while a blind one (`any`, `unknown`, an unconstrained type variable, an opaque result) must come through an explicit decoder that a reviewer can see, as `loadUser` does in the example. SepInfer's Node oracle already walks TypeScript ASTs and extracts declared types and JSDoc specs, so Phase 0 and the Phase 2 boundary can reuse it directly.

**The AI probe says what not to sell.** SepInfer generated 40 TypeScript modules with a current model from neutral tickets; 38 were `tsc --strict` clean (4,517 lines) and contained **zero soundly detectable type-soundness faults**, because the model used the same safety idioms as human code; the paper states plainly that one model under clean prompts "bounds nothing about worst-case output" (paper, "AI-Generated Code Probe"). Put beside Lee et al. and Bogner and Merkel, the picture is consistent: agents use escape hatches more, but nobody has shown that this produces more faults inside well-typed code. That is why Assured Script's value proposition is contracts that encode intent, pinned so agents cannot game them, plus checked boundaries, effects and taint for the security classes that stay flat, with soundness as the precondition rather than the product. The paper's complementary finding that TypePatrol, a dynamic detector it credits with finding a critical n8n CVE, works on surfaces disjoint from SepInfer's (paper, "Cross-Run Against a Dynamic Detector") supports runtime guards at the host boundary alongside static proof inside.

The research method transfers too. SepInfer pre-registered predictions, froze the analyser before a 150-repository out-of-sample run (six Class C sites in four repositories, none false), retracted three of its own claims in place, and ships an artifact that reproduces every derivation-path number offline; Phase 0 should be run the same way, and the author's Lean experience fits the job of mechanising the core calculus. SepInfer's honest limit transfers as a warning: its README's headline is that "ingesting real production TypeScript verbatim is the open problem", which is why the language should own a small sound core, and the same problem any annotation layer over ordinary TypeScript, LemmaScript included, has to face.

## A roadmap that earns the right to become a language

### Most of AS Lang's core should be replaced

Built and run, AS Lang matches the HANDOFF description, except that the Rust core is about 2,100 lines and lexer errors do carry line and column while every other error reports 0:0. A `cargo build --no-default-features` succeeds; `let`, `output`, `print`, `+ - * /`, `== < >`, `if` and type-annotation checks work; `x = 2` fails with "Unknown infix operator" because `=` has a precedence but no infix rule ([parser](../src/core/parser/mod.rs)); `%`, `!=`, `<=`, `>=`, `&&`, `||` and `!` fail with "not implemented" ([compiler](../src/core/compiler/mod.rs)); user-defined calls fail because the VM knows only `print`, arrays fail on the missing `MakeArray` handler, and indexing is never compiled ([runtime](../src/core/runtime/mod.rs)). Without assignment, loops cannot update their counters. One of four lexer tests fails on escaped quotes, and the README and `docs/EXPLAINER.md` still claim AVX2 SIMD, async/await, constant folding and "~10x faster than raw Python", none of which the code does ([build.rs](../build.rs) is a stub).

| Component | State today (built and run) | Decision |
|---|---|---|
| Cargo workspace, crate layout, MIT licence | Builds; default feature pulls in PyO3 | **Keep**; make PyO3 opt-in |
| Lexer | `f64`-only numbers, no string escapes, one failing test | **Replace**: spans on every token, `int`/`bigint`, escapes, template literals later |
| Pratt parser | No assignment, untyped parameters, return types never parsed, errors at 0:0 | **Rewrite**, keeping the Pratt structure; add spans and error recovery, which the LSP and agents both need |
| Type checker (`types.rs`) | Five types plus an `Any` that matches everything | **Replace** with a bidirectional checker for records, unions, generics-lite, refinements and effects |
| Bytecode compiler and stack VM | Many opcodes missing, one global variable table, no calls | **Retire** as the runtime; optionally rebuild as a small reference interpreter of the core IR for differential testing of emitted TypeScript |
| CLI and REPL (`main.rs`) | Works, with a `--debug` trace | **Keep** the shell; new subcommands `check`, `build`, `lock`, `fmt`, all with `--json` |
| LSP scaffold (`lsp.rs`) | Parse errors only, full sync | **Keep and extend**: real ranges, hover showing contracts and proof status |
| wasm-bindgen crate | Runs the interpreter in a browser page | **Keep**, repointed at the checker for the playground and for shipping the compiler as an npm package; whether Z3 runs acceptably as WebAssembly is an open engineering question |
| PyO3 module | `aslang.core.run_code` | **Park**; revisit only if a Python target is ever pulled for |

Rue shows an agent can build a language core "in roughly a week", and also that its green test suite was "lying" ([Rue](https://github.com/rue-language/rue/blob/trunk/website/content/blog/an-agent-holds-the-fort.md)), so the plan budgets for adversarial testing, not just construction. The thresholds are proposals to pre-register, not findings.

Phase 0 is what makes the plan cheap to test. With Dafny standing in for the sound core and LemmaScript as the strongest tool-not-language alternative, it answers whether a sound language with pinned contracts and sealed boundaries beats both tests and annotated TypeScript before a line of compiler is written, while the Action tests whether anyone wants the workflow at all. It is publishable either way (a SepInfer follow-up at a venue such as the SIGPLAN LMPL workshop or ICSE), and it fills open gaps: Lee et al. counted how often agents use `any` and assertions but not whether those cause failures, and nobody has measured how often agents weaken specifications.

The stop rules are there because most language projects never set any. Beyond the per-phase triggers, three events should make the author stop or pivot at any time: LemmaScript or a better-resourced player shipping verified TypeScript with boundary checks, effects and version-to-version contract pinning, and winning independent production users (Microsoft owns TypeScript and Copilot and its researchers lead F* and Verus work, while AWS runs Dafny in production and in July 2026 made the largest donation in the Lean FRO's history, framed around AI agents that "move money" ([Amazon Science](https://www.amazon.science/news/amazon-is-investing-in-the-lean-focused-research-organization); [AWS Newsroom](https://x.com/AWSNewsroom/status/2081807589776445754)); the right response then is to contribute rather than compete); evidence that pinned contracts are wrong often enough in practice that they pin bugs rather than prevent them; or Phase 0 showing that agents rarely weaken contracts, which would remove the lock's reason to exist. Funding needs to be decided early. Donation funding tops out low: Zig took in $670,672 in 2024 and warned it could not renew all contracts ([Zig Software Foundation](https://ziglang.org/news/2025-financials/)), and its biggest 2026 funding news was one individual's pledge of another $400,000 over two years ([Hashimoto](https://mitchellh.com/writing/zig-donation-2026)) [unverified]; Gleam runs on one sponsored developer ([Gleam 2024 survey](https://gleam.run/news/developer-survey-2024-results/)). Corporate money in 2026 flows to proof and to spec-as-source products (Amazon to Lean; an undisclosed seed round for CodeSpeak in February 2026 ([Preqin](https://www.preqin.com/data/profile/asset/codespeak/789233)) [unverified]), not to general-purpose independents. The realistic homes are a research position through Phase 1, then an industrial sponsor or a company; toolchains are strategic assets for AI companies, as Anthropic's purchase of Bun shows ([Anthropic](https://www.anthropic.com/news/anthropic-acquires-bun-as-claude-code-reaches-usd1b-milestone)).

## Why most new languages fail, and where this one could

The history is unkind, and the reasons are mostly extrinsic. The largest adoption study found that **open-source libraries, existing code and existing expertise drive language choice, while features such as performance, reliability and simple semantics do not**, with libraries influential for over 60% of respondents and simplicity for 25%, and that developers switch by domain rather than by linguistic similarity ([Meyerovich and Rabkin, OOPSLA 2013](https://lmeyerov.github.io/projects/socioplt/papers/oopsla2013.pdf)). JetBrains' 2026 migration analysis still finds project requirements the most common reason to switch, with Kotlin the one language people move to because they want to ([JetBrains](https://blog.jetbrains.com/research/2026/08/programming-language-migration/)) [vendor], and Kotlin had Android behind it ([Kotlin](https://kotlinlang.org/docs/android-overview.html)), as Verse now has Unreal Engine 6, whose Scene Graph Epic is building on it ([GamesBeat](https://gamesbeat.com/how-epic-games-plans-to-unify-its-developer-and-creator-ecosystems-using-verse-lore-and-unreal-engine-6-exclusive/)) [unverified]. **Soundness alone has never pulled developers off TypeScript**: ReScript, Elm and PureScript, sound compile-to-JavaScript languages available for a decade, together draw about 68,000 weekly npm downloads, roughly 0.03% of TypeScript's ([npm registry](https://registry.npmjs.org/rescript)). Timelines are long: Gleam took about eight years to 1.0 ([Gleam](https://gleam.run/news/gleam-version-1/)), Zig reached 0.16.0 in April 2026 with no 1.0 after roughly eleven years ([PyPI](https://pypi.org/pypi/ziglang/json)), Roc has no 0.1 after about seven ([Roc](https://github.com/roc-lang/roc)), MoonBit's 1.0 slipped from the first half of 2026 to the third quarter without shipping ([MoonBit roadmap](https://www.moonbitlang.com/blog/roadmap)), and Carbon has no 0.1 release ([Carbon roadmap](https://github.com/carbon-language/carbon-lang/blob/trunk/docs/project/roadmap.md)). Agents compress compiler construction, not stabilisation or ecosystem building. Projects stall when funding or people leave: Vale was archived, Austral went dormant, and Crystal's lead stepped back ([Crystal](https://crystal-lang.org/2025/09/29/wind-of-change/)). Admiration does not buy adoption: Rust tops Stack Overflow's 2025 admired list at 72.4%, ahead of Gleam at 70.8% and Zig at 64.2%, with Go at 56.5% and Python at 56.4% ([Stack Overflow 2025](https://survey.stackoverflow.co/2025/technology)) [unverified: decimals from a single search], and Rust's own users' top worry is still insufficient industry usage. The AI era adds a cold start: brand-new languages are "no-resource" for models, a June 2026 paper evaluates Gleam and MoonBit in exactly those terms ([arXiv](https://arxiv.org/abs/2606.16827)) [unverified numbers], 24 of 28 code-generation benchmarks focus on Python ([Liu et al., JSEP 2025](https://doi.org/10.1002/smr.70034)), and the gap between Dafny (82%), Verus (44%) and Lean (27%) on the same class of verified-synthesis tasks, which the benchmark's authors attribute to type-system complexity and training data, shows how much the language itself matters ([arXiv 2509.22908](https://arxiv.org/abs/2509.22908)). The cheapest measured remedy is documentation: on Pallas, a TPU kernel DSL rare in training data, curated documentation in context raised per-sample correctness from 5.8% to 37.3% ([JAXBench](https://arxiv.org/abs/2607.20466)) [unverified].

The plan answers each failure mode with a design choice rather than optimism. It borrows npm's libraries through emitted TypeScript and host imports instead of building an ecosystem, and emits validators in the interface those libraries already accept; it asks teams to adopt one module, with a free exit, instead of rewriting; it targets a domain (critical modules under agent-heavy workflows) rather than marketing itself as a sounder TypeScript, which the 0.03% figure shows does not sell; it keeps the surface small and TypeScript-shaped so models transfer what they already know, and ships curated docs, an agent skill and precise JSON diagnostics through npm; it replaces AS Lang's inflated README before anything else; and it forces a go/no-go decision in months, not years, against the rival most likely to make it unnecessary.

Real risks remain after those mitigations, and the author should weigh them plainly. The benefit is unproven until Phase 0 reports. Specification validation is the named grand challenge, and a wrong contract that is pinned becomes a pinned bug; example generation helps reviewers but does not solve it. The competitive window is already narrower than a year ago: LemmaScript occupies annotated TypeScript with a better brownfield story, the organisations best placed to ship contracts for TypeScript own most of the parts, and Dafny's JavaScript backend is a path for anyone who wants verified modules today. The boundary edge may prove smaller than claimed, since prototype pollution and type confusion are a minority of advisories and a Zod schema at each edge already catches much of what generated decoders would. The pure, immutable core will exclude code that real modules contain (async I/O arrives only in Phase 3), and SMT verification is brittle at scale; repository-scale benchmarks already report agents breaking existing proofs while rewriting code ([Vero](https://arxiv.org/abs/2608.13522)) [unverified]. The trusted base still includes Z3, the emitter and the JavaScript runtime. One person's bandwidth is finite, and the SepInfer submission comes first. Finally, the market may want the check and not the language; if Phase 0 says so, the right outcome is a successful tool or a contribution to LemmaScript and a good paper, not a stubborn compiler.

## Conclusion

The research changes the question more than it answers it. The scarce resource is no longer correct code but cheap, trustworthy evidence that code is correct, and the most valuable thing a language can do in 2026 is make that evidence small enough for a human to read and rigid enough that a machine cannot quietly rewrite it. The discovery that LemmaScript independently built SepInfer's floor guard into a TypeScript verifier cuts both ways: it is the strongest outside confirmation that models weakening specifications is a real, general failure, and it ends any pitch built on the lock alone. What remains distinctive sits where three findings meet: TypeScript's types are erased by design and will stay that way, agents reach for `any` far more often than people do, and every 2026 post-mortem fix found at a trust boundary was a runtime check someone wrote by hand. A language earns its place only if it writes those checks itself and refuses the escape hatches that make them necessary.

The second lesson is about ambition. The adoption history and the 2026 market say a small team wins only inside an ecosystem people already use, in a domain narrow enough to own, and by being honest about which rival might make it unnecessary. That argues for a language that looks, installs and exits like a TypeScript tool, and for a first deliverable that could tell the author not to build it, or to build on LemmaScript instead. If Phase 0 shows that a sound core with pinned contracts and sealed boundaries beats both tests and annotated TypeScript for agent-written code, the result matters well beyond one language; if it shows it does not, the author will have learned it in three months instead of eight years.
